An electronic stock exchange is one of the most demanding problems in backend systems design: thousands of buy and sell orders hit the matching engine concurrently, every trade must balance cash and equities without losing a cent, and latency must stay within milliseconds.

Building my **Miniature Electronic Stock Exchange Simulator** in Java, Spring Boot, PostgreSQL, and Redis forced me to confront the fundamental tension in distributed systems:

> **How do you maximize concurrent throughput without compromising transactional atomicity?**

A financial ledger that drops an update or records a half-settled trade is fundamentally broken. Here is how I designed the matching pipeline, enforced price-time priority, implemented row-level locking, and prevented concurrent deadlocks.

## The Matching Algorithm: Price-Time Priority (FIFO)

An order book holds two queues:
- **Bids (Buys)**: Sorted by **Highest Price First**; ties broken by **Earliest Timestamp**.
- **Asks (Sells)**: Sorted by **Lowest Price First**; ties broken by **Earliest Timestamp**.

When an incoming **Limit Order** arrives, the matching engine evaluates the opposing side of the book:

```java
public class OrderBook {
    // Priority queues for fast top-of-book lookup
    private final PriorityQueue<Order> bids = new PriorityQueue<>(
        Comparator.comparing(Order::getPrice).reversed()
                  .thenComparing(Order::getTimestamp)
    );

    private final PriorityQueue<Order> asks = new PriorityQueue<>(
        Comparator.comparing(Order::getPrice)
                  .thenComparing(Order::getTimestamp)
    );

    public List<Trade> matchOrder(Order incoming) {
        List<Trade> executedTrades = new ArrayList<>();

        if (incoming.getSide() == Side.BUY) {
            while (!asks.isEmpty() && incoming.getRemainingQuantity() > 0) {
                Order topAsk = asks.peek();
                if (incoming.getPrice().compareTo(topAsk.getPrice()) < 0) {
                    break; // Price condition unsatisfied; rest on book
                }
                executeTrade(incoming, topAsk, executedTrades);
            }
            if (incoming.getRemainingQuantity() > 0) {
                bids.add(incoming);
            }
        }
        return executedTrades;
    }
}
```

A trade occurs whenever:

```text
Bid Price >= Ask Price
```

The execution price is always determined by the **resting order** (the maker), rewarding liquidity providers.

## The Concurrency Bottleneck: To Lock or Not to Lock?

If multiple worker threads execute trades concurrently, race conditions immediately arise:
- **Double Spending**: User A has 10,000 USD balance and fires two concurrent buy orders for 8,000 USD each. Both check `balance >= 8000`, both pass, and the account goes -6,000 USD.
- **Lost Trades**: Two incoming market buy orders match against the exact same 100 shares of resting ask liquidity.

There are two primary paradigms to solve this:

### 1. Global Coarse-Grained Synchronization
Wrap the entire order book and ledger in a single mutex.
- *Advantage*: Trivial to reason about; zero race conditions.
- *Fatal Flaw*: Total throughput collapses. Order placement on AAPL serializes orders on MSFT.

### 2. Fine-Grained Row-Level Database Locking
Leverage PostgreSQL's `SELECT ... FOR UPDATE` row locks to protect only the exact user accounts and orders touched by a trade.

## Atomic Settlement with Pessimistic Row Locking

Every matched trade requires updating four balances:
1. Buyer Cash: `-Trade Value`
2. Seller Cash: `+Trade Value`
3. Buyer Equities: `+Quantity`
4. Seller Equities: `-Quantity`

This must occur inside a single atomic `@Transactional` boundary with strict `SELECT FOR UPDATE` locking:

```java
@Service
public class TradeSettlementService {

    @Autowired
    private PortfolioRepository portfolioRepo;
    
    @Autowired
    private TradeAuditRepository tradeAuditRepo;

    @Transactional(isolation = Isolation.READ_COMMITTED)
    public Trade settleTrade(TradeCandidate candidate) {
        // Enforce consistent global lock ordering to eliminate deadlocks
        Long firstId = Math.min(candidate.buyerId(), candidate.sellerId());
        Long secondId = Math.max(candidate.buyerId(), candidate.sellerId());

        Portfolio p1 = portfolioRepo.findWithLockById(firstId);
        Portfolio p2 = portfolioRepo.findWithLockById(secondId);

        Portfolio buyer = candidate.buyerId().equals(firstId) ? p1 : p2;
        Portfolio seller = candidate.sellerId().equals(firstId) ? p1 : p2;

        BigDecimal totalCost = candidate.price().multiply(BigDecimal.valueOf(candidate.quantity()));

        // Verification under exclusive lock
        if (buyer.getCashBalance().compareTo(totalCost) < 0) {
            throw new InsufficientFundsException("Buyer cash deficient");
        }
        if (seller.getHolding(candidate.symbol()) < candidate.quantity()) {
            throw new InsufficientSharesException("Seller equity deficient");
        }

        // Atomic Mutating Operations
        buyer.deductCash(totalCost);
        seller.addCash(totalCost);
        buyer.addShares(candidate.symbol(), candidate.quantity());
        seller.deductShares(candidate.symbol(), candidate.quantity());

        Trade executedTrade = new Trade(
            candidate.symbol(), candidate.price(), candidate.quantity(),
            candidate.buyerId(), candidate.sellerId(), Instant.now()
        );

        return tradeAuditRepo.save(executedTrade);
    }
}
```

The repository utilizes explicit SQL pessimistic write locks:

```java
public interface PortfolioRepository extends JpaRepository<Portfolio, Long> {
    @Lock(LockModeType.PESSIMISTIC_WRITE)
    @Query("SELECT p FROM Portfolio p WHERE p.id = :id")
    Portfolio findWithLockById(@Param("id") Long id);
}
```

## Eliminating Deadlocks via Consistent Global Ordering

In a concurrent exchange, users trade back and forth simultaneously. Consider this scenario without ordering:

- **Thread 1**: Settles Trade between User 42 and User 87.
  1. Acquires lock on User 42.
  2. Attempts to acquire lock on User 87... (Waits)
- **Thread 2**: Settles Trade between User 87 and User 42.
  1. Acquires lock on User 87.
  2. Attempts to acquire lock on User 42... (Waits)

**Result**: Classic **Cyclic Deadlock**. Both transactions stall until the PostgreSQL deadlock detector kills one of them with an error:
`ERROR: deadlock detected - Process 14022 waits for ExclusiveLock...`

The solution is an absolute rule of concurrent systems: **Always acquire locks in a globally consistent order.**

```java
Long firstId = Math.min(candidate.buyerId(), candidate.sellerId());
Long secondId = Math.max(candidate.buyerId(), candidate.sellerId());
```

By ensuring that every thread in the application locks the lower ID before the higher ID, circular wait conditions become mathematically impossible. Deadlock frequency dropped to **zero**.

## Decoupling the Hot Path with Redis and Kafka

Disk-bound relational databases cannot sustain millions of reads per second. We separate the architecture into two paths:

1. **The Fast Path (Redis)**:
   - Maintains the active top-of-book market depth.
   - Serves sub-millisecond Level-2 market data reads directly to client WebSockets without touching PostgreSQL.
2. **The Durable Path (PostgreSQL & Kafka)**:
   - PostgreSQL owns the durable ledger, user accounts, and trade history.
   - Kafka asynchronously fans out executed trade events to downstream notification services, trade receipt generators, and analytical data lakes.

## Systems Takeaways

1. **Isolation levels are financial invariants.** `READ COMMITTED` combined with explicit row locks (`SELECT FOR UPDATE`) provides repeatable-read safety for targeted rows while avoiding transaction serialization aborts.
2. **Deadlocks are architectural bugs.** You do not fix deadlocks with retry loops; you fix them with deterministic lock ordering across all execution paths.
3. **Separate truth from telemetry.** Your database must guarantee durability and balance preservation; an in-memory cache like Redis should serve read-heavy orderbook inspection.
